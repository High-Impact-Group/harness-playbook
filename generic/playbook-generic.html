The idea

For us, a design, an adversarial review, a build, an independent code review and a deploy gate catch real defects. They also cost hours and a lot of tokens. For a typo or a cold-path tweak that cost buys very little.

This is how we work at High Impact Group. We share it as it is, not as a standard or a recommendation. It does not depend on any one AI tool or vendor. Take what is useful and change the rest to fit your own stakes.

Pick the process by risk. Size is a poor guide. Start every change at the lowest tier that fits. Go up only when a named trigger applies. Keep the full process for the few kinds of change where a mistake is expensive or hard to undo.

Four tiers

TIER 0CI only
  • Docs, tests, copy
  • Tooling and configuration
No design. No review.
TIER 1 · the default for codeLight
  • Cold path, small, easy to revert
  • Covered by a test that can fail
A few lines of design in the PR. No independent reviewer unless the owner asks.
TIER 2Standard
  • Shared helpers, generators
  • Prompt wording, scheduled jobs, anything that sends to a customer
Short design in the PR. One reviewer reads design and diff together.
TIER 3Full process
  • Migrations, money, auth, privacy
  • Your product's core loop
Design file. Two or more design reviewers. The reviewer runs every mutation.

How to assign a tier

  • Start low. Tier 1 is the default for code. Tier 0 for docs, tests and config.
  • Escalate on a named trigger only. Keep a short table of triggers in your repo. "It feels risky" is not a trigger. If you cannot name the row, stay put.
  • Never go back down after a trigger fires. Whoever finds the trigger raises the tier and says so.
  • Write the tier in the PR on one line. A CI check can fail PRs that have no tier line.
  • The owner can override with one word: "tier 1".

Our trigger table is built for our own stakes, and yours will differ. Our Tier 3 rows: schema migrations, deleting or rewriting stored user data, billing, auth and access control, privacy-sensitive data, and the one code path your product depends on. Our Tier 2 rows: shared helpers, generated customer-facing documents, prompt changes, and scheduled jobs.

The five gates (Tier 3)

G1 Design
designer

A design file: evidence, at least two options, files to change, tests, rollback, acceptance checks.

G2 Design review
design reviewer

Told to find reasons the design is wrong. Not the author. Every must-fix is answered.

G3 Build
builder

Tests first, shown failing. Builds exactly the approved design. Opens a draft PR.

G4 Code review
code reviewer

Wrote neither design nor code. Reads the full diff, drives the real path, runs the mutations.

G5 Deploy
a person

Only after G4. Migrations, environment values and flag flips are done by a human.

Roles

A role can be filled by a person or by an AI agent. What matters is that each role has one job, a stated level of access, and a different holder from the roles it checks.

Reviewers must not have written the thing they review. Say who you chose and why. If every independent reviewer is busy, wait or record an exception on the PR.

Pin the model and effort for each role

We do not leave model choice to defaults. We record the model and the effort level for each role in a file in the repo, and a script checks that the roles match that one file.

A config check

Keep one file that lists the allowed models and the pin for each role. A small script reads every role definition and fails CI when one disagrees, a model is not on the list, or a reviewer gained write access. This has been the cheapest way for us to keep a large set of agents consistent.

Guardrails in code, not in prompts

A written instruction can be ignored, so we enforce the rules we cannot afford to break with checks that run before an action takes effect: command guards, permission deny lists, branch protection and CI.

What we always block, and always check

  • Plain force pushes (allow the lease form)
  • Ending a task while the fast checks fail (a check runs them and sends the work back)
  • Recursive deletes on protected paths
  • Piping a download into a shell
  • Edits to secrets, lock files and keys (exempt example files)
  • Closing keywords in commits and PRs, if you hand bugs to a tester
  • A guard that crashes: make it stop the action, not let it through

Where we want a person to decide

  • Merging and marking a PR ready (the owner, or a deployment-manager session the owner directs)
  • Opening a non-draft PR
  • Pushing to the main branch
  • Applying production migrations and changing production environment values

Parse commands properly. A substring match blocks harmless commands and misses wrapped ones (a shell run through another shell, subshells, global flags before the verb). Test each guard with sample inputs, then confirm once in a live run that it fires.

Three long-running sessions

Besides the roles above, we keep three persistent AI sessions, each with one fixed job and its own brief. A person starts each one, states the authority once, and stays on the decisions that are theirs.

Delivery controller

Runs a delivery program. It writes little code itself. It assigns each change a risk tier, briefs the design, review, build and test roles, and checks each result against the code, the database and the logs before it believes it.

  • States the model and effort for every role it briefs, every time.
  • Never lets the author of a design or a change review it.
  • Keeps a handover document so a new session can resume from the repo alone.
  • Leaves to the owner: migrations, production flags, anything paid or irreversible, and closing bug reports.

Deployment manager

Takes a list of pull requests and an order, and walks each one to merged: brings the branch up to date, resolves conflicts, runs the tests, fixes what only breaks because two changes now meet, turns on auto-merge, and waits for the checks.

  • Merges one at a time, and prepares the next while the current one waits.
  • Holds a change whose description names an unmet precondition, and says what would close it.
  • Never weakens a test, rewrites history or force-pushes.
  • Reports what it changed beyond the change, what it did not check, and what only a person can do.

Smoke tester

Uses the live product through a browser the way a customer would. It finds problems, proves them with evidence and files them as issues. It does not fix them.

  • Waits until a deploy is live before testing, and uses fresh test data each round.
  • Closes an issue only after it has seen the fix work on production.
  • Probes AI features with injection, disguised injection, pressure to invent figures, off-topic requests, regulated advice and requests to name real people. It always sends a normal follow-up afterward.
  • Leaves logins, sends and deletions to the person, and says what it did not test.

The common rule is that these sessions report faithfully: a failure is stated with its evidence, a skipped step is stated as skipped, and a check is never claimed that did not run.

Working rules

  • PRs open as drafts. The owner, or an agent they direct, marks them ready and merges after review and green CI.
  • Link issues without closing keywords (on GitHub, refs #N instead of fixes #N). Let the tester close after retest.
  • One fix round per review. Fix critical and high findings and clear bugs. Put nits in a follow-up note. A reviewer with nothing blocking says "ship" and stops.
  • Tests first, shown failing on the base. State a rollback. Give source, time window and sample size for every telemetry claim.
  • A builder that cannot build the design as written stops and reports. The fix is a design amendment, not a quiet deviation.
  • Retest on fresh data. A defect on rows written before a fix is not proof the fix failed.
  • Scale mutation checks with the tier: none at Tier 1, the important ones at Tier 2, all at Tier 3.
