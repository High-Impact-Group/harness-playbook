# feature-summary

Write a clear, non-technical summary of the product, or of one named feature. The readers are stakeholders, clients and the wider team. They are not developers.

## Steps

1. Read the README, the project instructions file and the main page or route files. Learn what the product does.
2. If a feature is named, focus on that part of the code. If not, summarize the whole product.
3. Check what is built and working. Use only what the code shows. Do not describe plans as features.

## Writing style

- Plain US English. No jargon and no technical terms.
- Say what the feature does for the user. Do not say how it is built.
- Short sentences and a clear structure.
- Give concrete examples of what a user does.
- Write for a senior business leader.

## Structure

**Name.** The product or feature.

**What it does.** Two or three sentences.

**Who it is for.** The target user.

**Key capabilities.** For each major capability: what the user can do, why it matters (the benefit, not the mechanism) and one example scenario.

**How it works, from the user's side.** Walk through a typical journey from start to finish. Say what the user sees and does at each step.

**Included now and coming later.** The current state, plus any planned or unfinished work that is visible in the code. Label it clearly.

## Output

Save to `docs/feature-summary.md`. Keep it to about two pages (roughly 800 words). When you cover many features, give each three or four sentences and a short capability list.

## Guardrails

- Never invent a capability, number or customer. If the code does not show it, leave it out.
- Do not promise dates for planned work.
